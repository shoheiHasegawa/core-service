# Integration Test (結合テスト) の制約と責務

## 1. 配置と境界の厳格化
- `tests/integration/` は、**公開Service仕様（In-Out）を固定し、要求シナリオの100%を網羅する**ための防波堤（ハーネス）である。
- **配置**: `tests/integration/` 配下には、`application/` などのレイヤー階層は作らず、直接ドメイン名（機能名）のディレクトリ（例: `task_management/`）を配置すること。結合テストの起点は常に Application層（ユースケース）であるため、レイヤー分類は不要である。
- **境界とDB接続の厳格化**: テストの境界は「Application層からインフラ実体（DB等）まで」とする。システムの層間における**Mock（モック化）を一切禁止**し、必ずテスト用DB（インメモリSQLite等）へ接続させること。

## 2. 許容されるMock (Fakeの注入)
Mockが許されるのは外部API通信のみ。現在時刻やUUIDなどの非決定的な値は、DIコンテナ経由で `FakeClock` などを注入すること。

## 3. テストの粒度とグルーピング基準 (Grouping Principle)
- **ライフサイクル（一連のCRUDストーリー）**: ノート登録・検索・更新などの流れるような業務フローは、1つの統合テスト関数にまとめて効率的かつ高速に検証する。
- **前提条件が異なる関心事（セキュリティ・異常系・独立監査）**: ディレクトリトラバーサル防御やルール違反監査など、前提や検証目的が独立しているものは別テスト関数に明確に分離する。

## 4. Integration Test の Helper 実装ルール (共通の型)
- `tests/integration/helpers/` に、結合テスト専用の「共通の型」を配置することを義務化する。
  - **`IntegrationTestContext`**: `agent-core` の振る舞い（DI組み立て）を模倣し、テストDBの初期化や具象Repositoryの注入を担う「実行環境の型」。
    - ⚠️ **State Leakage（状態汚染）の防止**: 各テスト終了時に必ず「トランザクションのロールバック」またはDBの初期化を行う責務を持つこと。
  - **`TestDataBuilder`**: テストデータを生成しDBに事前投入するための「データ生成の型」。

## 5. 必須仕様シナリオ（6大観点マトリクス）
すべての機能仕様書（`spec.md`）およびそれに対応する結合テスト（`tests/integration/`）は、以下の **6大テスト要求シナリオ・マトリクス** を網羅して定義・検証されなければならない。

1. **Happy Path (主系)**: 主要な入力に対する期待される正常な出力と状態変化。
2. **Idempotency & Lifecycle (冪等性・ステートフル再実行)**: 同一操作・ジョブが複数回連続実行された場合でも、重複生成・副作用・時刻破壊が発生せず冪等であること。再起動・途中中断後の再実行耐性。
3. **Boundary & Midnight (境界値・日跨ぎ・空データ)**: 日付境界（00:00跨ぎ）、上限/下限、空データ、最大件数時に破綻しないこと。
4. **Reconciliation & Drift (外部SoRとの差分調停)**: 外部SoR（カレンダー/外部ファイル）との同期において、手動変更とローカルデータの整合性が正しく調停されること。
5. **Fault Tolerance (異常系・部分障害・データ破損耐性)**: 一部のストレージ/APIが失敗した場合に安全にフォールバック/スキップされ、不正・破損データが混入した際に安全に隔離されること。
6. **Domain Invariants (ドメイン不変条件)**: システムが常に満たすべき絶対原則（重複配置の完全排除、安全制約の死守など）が数学的に維持されること。
